## Phase 4b, built this session

`shadowfleet/detect/`: `sts.py`, `loitering.py`, `draught.py`, `spoof.py`, `churn.py`, driven by
`make detect`, reporting into `reports/phase4b.md`. Tables land in `data/parquet/detect_*` with a real
`observed_at` on every row.

Three decisions that depart from the phase prompt, all now ADRs in the plan:

- **ADR-19, no polygons.** The prompt says STS and loitering must be "outside port polygons". DMA already
  carries the vessel's own `nav_status`, so "at a berth" is a hull reporting Moored: one predicate instead
  of a hand-drawn polygon set whose errors nobody here could check. Hulls *at anchor* are kept on purpose,
  because the Skagen transfers happen at anchor. Every event carries its position, so the anchorages are
  reported from the output (`by_cell`) rather than asserted in advance. This also retires the PLACEHOLDER
  Skagen box from the critical path.
- **ADR-20, spoof excess is an incidence difference.** See "what the rehearsal caught" below.
- **ADR-21, no hull id during a vessel's first window.** Records from the warm-up are dropped rather than
  given an MMSI-derived id, because a synthetic id splits the hull's history at the boundary and its first
  real transition vanishes. That actually happened to a 4 m draught change in a test.

## What the dress rehearsal caught

Phase 3 and 4b had only ever run on 6-to-9-day fixtures, so this session built a 210-day, 300-hull,
2.1M-row synthetic store and ran ingest -> phase1 -> identity -> detect over it before any of it touches the
928-day store. Timings were reassuring (84 s to ingest, about 5 s for every analysis stage combined), but it
found a real bug that no unit test could:

**mean spoof excess was -0.05 across 40,000 hull-days.** A difference from a fleet-wide baseline cannot be
systematically negative. `jump_baseline.frac_jumped` is the share of *vessels* in a 0.5-degree cell that
jumped that day; the code was subtracting it from the share of a hull's *rows* that were jumps. Different
units. The hull's side is now "did this hull jump today", so both sides are per-vessel incidences, and over a
180-day window this aggregates into PREREG's `spoof_jump_rate_excess`. `CLAUDE.md` described it correctly
from the start; only the code was wrong. The test now pins exact values (0.0 when a whole cell jumps, 0.75
for the one jumper in four, -0.25 for the quiet three), which a per-row rate cannot produce.

It also showed that the resolver warm-up eats about 14 percent of MMSI-days in a 7-month store, which is why
`reports/phase3.md` prints both `share_by_imo` (strict, warm-up counted against it) and
`share_by_imo_of_mapped` (the resolver's own hit rate). On real data the gap should be smaller.

## Phase 5a, also built this session

`shadowfleet/features/asof.py`: `features(hull_id, T)` over records with `observed_at <= T`, 32 features in
the seven PREREG families, written to `feature_matrix/cutoff=T/` by `make features`. About 2 s per cutoff for
312 hulls on the rehearsal store.

`tests/test_leakage.py` has leakage tests (a) and (b) for real: (a) compares features at T against a store
whose later partitions are physically deleted; (b) is static analysis over `features/` plus a check that the
registry's families equal PREREG section 7 and that each family is actually named in `PREREG.md`. Tests (c)
permutation, (d) reverse-time and (e) entity-resolution sensitivity need a fitted model, so they are Phase 5b
hooks — named in `reports/phase5a.md` so their absence is visible rather than forgotten.

One feature was renamed in the process: `n_laden_transits` was counting static messages above the hull's
75th-percentile draught, which is a misnamed feature. It is per transit now, because the count of laden
transits approximates liftings whereas a share of laden messages sits near one half for anything doing round
trips.
