## Why it feels like circles

Every live source has broken on first contact, each in a way no fixture could have shown:
DMA moved its bucket; OFAC's archive dates had two-digit years; the EU source was the wrong dataset; and
today the ITU MID table broke four times (moved URL, dependencies spelled "Parent - Territory", multi-MID
countries in one cell, one MID shared by three territories). None of that was avoidable in advance. GFW is
the one source that has not had its turn yet, so expect one more loop there, and then it stops.

Three of today's problems were self-inflicted by the hand-off itself: `git reset --hard` onto a bundle
wiped uncommitted regenerated files twice, and once removed a real commit. **From now on the hand-off is
`git pull --ff-only <bundle> main`**, which refuses instead of overwriting, and every bundle is rebased
onto what is on GitHub first.

## Phase 3 findings that need a decision

1. **Fragmentation.** Of 20 designated IMOs checked, none maps to a single hull id; a typical one is split
   across 4-5 ids, one real and the rest `syn:`. Those hulls changed MMSI several times, and the
   MMSI-windows that never broadcast an IMO get their own synthetic id. Features computed per hull id
   would see a fraction of each of these hulls' histories, and these are exactly the hulls the project is
   about. Needs a look before Phase 5a.
2. **47 later-designated hulls never reported tanker class.** The 4,096 "tanker-sized but never
   tanker-class" MMSIs are mostly offshore and wind-farm vessels (the examples are Wind Osprey, Brave
   Tern, a jack-up rig), but 47 of them were later designated. If those are real tankers mis-typed in
   AIS, rule 3's population is missing positives. Needs a hand look at the 47.

## Corrections, later on Sep 28

**Phase 4a was never built.** The table above originally said its code was "written from docs". What
exists is the Phase 0 probe and a few response helpers. Nothing writes `gfw_events`, so the eleven GFW
features (gaps, encounters, loitering, port visits, Russian port visits) read an empty table: about a third
of the feature set, including B2's two heaviest terms after B1 (`long_gap`, `sanctioned_partner`). It is
being built next, against the real responses the Phase 0 probe cached.

**The fragmentation finding is a rule-3 violation, not a cosmetic one.** Reproduced synthetically in
`tests/test_identity_attribution.py`: hull ids were stamped as known when each record was written, so a
vessel whose IMO resolved partway through a feature window appears under two ids at one cutoff, and the
`syn:` fragment of a vessel listed before the cutoff stays in the population, which rule 3 forbids. Such
fragments can also never carry a positive label. The fix is to assign hull ids as known at the cutoff: at
T, every record of a transmitter goes to the hull that transmitter maps to at T. That uses nothing after
T, so it stays point-in-time, and it lets the detectors keep records from a vessel's first 30 days, which
ADR-21 had to drop. Recorded as ADR-23. It touches Phases 3, 4b and 5a, none of which has been run on real
data past Phase 3, so nothing has to be redone.

Revised estimate: the fix and Phase 4a add roughly two sessions on the code side. Still 3-4 weeks overall.

## Later still on Sep 28: both fixed

- **ADR-23 landed.** Hulls are assigned at the cutoff. The three rule-3 tests that reproduced the leak pass,
  a cutoff one day before a vote closes is pinned, and detectors now keep the first-30-day records they used
  to drop. `make identity` has to be re-run on the real store: `syn:` ids no longer hash the name, and
  identity intervals are now keyed by transmitter.
- **Phase 4a is built**: `make gfw`. Vessel ids by IMO, events in batches of 25 vessel ids per call and one
  calendar year per call (the only shape the live API has been seen to accept), cached and resumable. All
  64 real events in the Phase 0 cache parse, and the eleven GFW features are computed at the cutoff.
- **B1 amended, with Adam** (PREREG section 12): Russian Baltic and Black Sea ports plus Murmansk;
  Kozmino removed; Kaliningrad and Baltiysk added. GFW port visits match by country and position, since
  2 of the 8 real Russian port visits had no anchorage name.
- **Still to check on real data:** DMA's free-text `destination` often carries UN/LOCODEs (`RU ULU`,
  `RULED`) rather than port names. If so, `share_russian_destination`, the DMA half of B1, undercounts.
  One query on the real store settles it.

## Sep 29

- **B1's DMA half fixed.** The destination check confirmed it: 1,215 of the top 1,462 Russian-looking
  destination pairs were UN/LOCODEs or spelling variants the name list missed (about 83%). Destinations now
  match by LOCODE (verified) or by normalised name; Arkhangelsk stays out. Recorded as a pre-results PREREG
  amendment. 237 tests pass.
- Next on real data: `make detect`, then `make features`, `make backtest`, `make phase6`.
- **Churn fixed, and it is a finding.** Counting from broadcasts, 2 IMO changes under a stable MMSI in 31
  months. Identity change in this fleet happens by changing MMSI (reflagging), which the feature store counts
  at each cutoff; changing the IMO under a kept MMSI essentially does not happen in Danish waters.
- **Reruns were not reproducible.** Draught changes came out 63,726 then 63,609 on identical data: rows
  stamped the same instant were ordered arbitrarily. Draught now ignores an instant with two different
  readings; a name or callsign that conflicts at one instant now counts as unknown there, the same rule.
- **Identity intervals were mostly noise.** 471,532 intervals for 6,605 MMSIs: 460,732 were callsigns
  alternating with DMA's "Unknown" placeholder, and most name changes were one-day decode garbage
  ("KAIFANA*#", "YERCURIUS" for MERCURIUS). Placeholders are now missing values, and a name or callsign
  counts from its 2nd day under an MMSI. `days_since_last_identity_change` now counts only the changes the
  other identity features count. All pre-results.
- **After that: 16,773 intervals** (from 471,532). Two residuals handled: names with symbols no ship name
  uses (`*#%$^<>` and so on) are garbled messages even when they repeat, so they are now missing; and
  `n_name_changes` counts distinct names beyond the first, so two units taking turns on one MMSI (TORILL
  KNUTSEN / HAVFISK, 500 intervals) is one extra name, not 250 renames. Known residual: MMSI 447173000
  (KAIFAN, Kuwait) has a faulty unit whose letters-only garbage repeats; it will show up as a high name count
  and belongs in the false-positive review, labelled "AIS fault".

## Oct 2: first backtest

- Features built: 20 monthly cutoffs (Aug 2024 to Mar 2026), ~2,550-2,760 hulls each, 32 features, GFW in.
- **Leakage test (d), reverse time, failed:** training on Mar 2026 and scoring Aug 2024 gave PR-AUC 0.110,
  versus 0.044 the normal way round (ratio 2.5, limit 1.5). Not yet known whether this is real leakage or
  the two cutoffs' different base rates (the Aug 2024 horizon contains OFAC's Jan 10 2025 wave).
- **Harness bug:** it printed all metrics despite the failure. Fixed (it now stops); disclosed in PREREG
  section 12, so every later change is post-hoc.
- The rerun prints base rates and lift beside the pre-registered ratio, to tell the two explanations apart.
- **Diagnosed: base rate, not leakage.** Base rate 4.68% at Aug 2024 vs 0.65% at Mar 2026. Per unit of base
  rate, backward (2.36x random) is worse than forward (6.70x), the opposite of a leak. Adam chose to amend
  (d) to compare lift; post-hoc, recorded in PREREG section 12, and the README and phase5b report both
  show the raw rule failing beside it.
- **Backtest passes (d) on lift; first official results.** Primary endpoint (union label, B1 stratum,
  precision@50): random 0.124, B1 rule 0.147, logistic 0.166 (13 cutoffs), B2 weighted rules 0.207,
  LightGBM 0.208 (13 cutoffs), isolation forest 0.245. Caveat found: LightGBM and logistic only score the 13
  cutoffs with a closed training horizon, the later and lower-base-rate ones, so the all-cutoff averages
  are not comparable. Reports now add a matched-cutoff table (post-hoc presentation, same numbers).

## Oct 2: Phase 6, first run (before the two LightGBM fixes)

Matched cutoffs (13, union label, B1 stratum), precision@50 / PR-AUC: random 0.069 / 0.085, B1 rule
0.099 / 0.071, B2 rules 0.160 / 0.094, logistic 0.166 / 0.147, isolation forest 0.186 / 0.174,
**LightGBM 0.195 / 0.199**. On matched cutoffs LightGBM leads; the isolation forest's all-cutoff lead came
from scoring the early high-base-rate cutoffs that LightGBM cannot.

- Signal is Russian trade plus size: top SHAP drivers are share_russian_destination, n_russian_port_visits,
  days_since_last_russian_port_visit, length_m. Dropping GFW port visits costs the most PR-AUC at nearly
  every cutoff.
- Identity features hurt: dropping them raises PR-AUC at most cutoffs, and their PSI is 0.5-0.96 (severe
  drift) because they are lifetime counts that grow with time since the data starts. A design flaw, reported.
- GFW encounters contribute nothing (5 events in the population). Only 2 cutoffs fall after the Hormuz break.
- Two problems found and fixed (PREREG section 12): LightGBM was not reproducible between runs, and early
  stopping never ran. Phase 6 must be re-run.

## Oct 2: Phase 6 after the two fixes (the numbers that count)

Matched cutoffs, precision@50 / PR-AUC: **LightGBM 0.168 / 0.141** (was 0.195 / 0.199 with the bugs),
logistic 0.166 / 0.147, isolation forest 0.186 / 0.174, B2 rules 0.160 / 0.094, random 0.069 / 0.085.
Fixing early stopping to match the pre-registration made LightGBM worse, and the pre-registered number is
the one reported. Every non-trivial model lands between 0.16 and 0.19, about 2.3-2.7x random: the
cooperative data carries a modest signal that no model here extracts much more of. Several restricted
ablation arms beat the full model (drop_ais 0.199, drop_identity 0.186, gfw_only 0.179 precision@50),
consistent with noisy features and a small positive count.

Also fixed: Phase 6 flagged lists (`reports/flagged_*.csv`) carry GFW-derived feature values and are now
gitignored (rule 7); a test checks every GFW-derived output path is ignored.
